[#backup-restore-velero]
== Backing up and restoring with Velero

https://docs.apps.rancher.io/reference-guides/velero[Velero] provides a framework for backing up and restoring {productname} deployments on supported {kube} clusters.
It captures the {kube} API objects of the registry and the data in the persistent volumes that the registry uses.
This approach protects the registry configuration and the container images stored in the cluster against accidental deletion or cluster failure.

[#pr-velero-before-you-start]
=== Before you start

Velero protects {productnameshort} by backing up {kube} resources and persistent data.
In most cases, it is the recommended backup method for registry deployments on {kube}.

The scope of the backup depends on whether the registry database and image storage run inside or outside the cluster:

* *Internal {postgresql}:* Velero backs up the registry resources and the data volume for the internal {postgresql} database, but you must also create a separate database-level backup for application consistency. This is the registry database, not the Kubernetes etcd data store.
* *External {postgresql}:* Velero backs up the registry deployment and its {kube} resources. Protect the external {postgresql} database and the external object storage with the native backup tools of the database or the cloud provider.

Velero does not back up {redis} data.
{redis} mainly holds sessions and caches, so users must log in again after a restore.

[IMPORTANT]
====
For a full disaster-recovery workflow, the Velero backup repository must be separate from the cluster where {productnameshort} runs.
A cluster-local backend such as `local-path`, a PVC-backed store, or an NFS-backed store is not a portable production backup target.
Velero stores backups in an object store, and it does not provide a PVC-backed or NFS-backed `BackupStorageLocation` that supports a full-cluster recovery workflow.
====

[#pr-velero-prerequisites]
=== Prerequisites

Before starting the backup process, make sure you have the following:

* A supported {kube} cluster and a {productnameshort} release that is compatible with both the cluster and the Velero version you use.
* {helm}, `kubectl` and the https://velero.io/docs/main/basic-install/[Velero CLI] installed.
* A Velero server with the storage-provider plugin that your object store requires. To install Velero and its plugins from {sappco}, see the {sappco} documentation on link:https://docs.apps.rancher.io/get-started/deploy-helm-chart[deploying a {helm} chart] and the link:https://docs.apps.rancher.io/reference-guides/velero[Velero reference guide].
* An off-cluster `BackupStorageLocation` for production use.
* For File System Backup, the Velero node agent running in the cluster. Enable it with `deployNodeAgent: true` in the Velero {helm} chart.
* For CSI volume snapshots, a CSI driver that supports snapshots and a `VolumeSnapshotClass` that is labeled `velero.io/csi-volumesnapshot-class: "true"`.
* A recovery cluster that provides the same `StorageClass` names as the source cluster, so that the restored PVCs can bind.

[#pr-velero-storage]
=== Recommended storage configuration

For production environments and full disaster recovery, use a storage backend that is independent from the primary cluster.
This keeps backups available even if the cluster is lost or the registry namespace is deleted.

Supported backup backends include:

* Amazon S3
* Azure Blob Storage
* Google Cloud Storage
* Any other approved Velero provider plugin

For the complete supported-provider list, see the https://velero.io/docs/main/supported-providers/[Velero supported providers] page.

[#pr-velero-expectations]
=== What to expect after a restore

A successful backup does not preserve every runtime state.
After a restore, expect the following:

* *Lost memory data:* The registry keeps repository and artifact pull times in memory and writes them to the database periodically. Any data that was not yet written to the database is lost. This typically has a low impact on operations.
* *Lost user sessions:* The {redis} volume is excluded from the backup, so all active sessions are lost and users must log in again.
* *Hanging tasks:* Replication, garbage collection and security scans can remain in a pending or interrupted state and must be restarted or stopped manually from the administrator interface.
* *Crash consistency:* Velero volume snapshots are crash-consistent. This protects the storage state after a crash, but it does not guarantee that the database transactions are complete. For a production deployment with an internal {postgresql} database, also create an application-consistent database dump.

[#pr-velero-backup]
=== Backing up {productnameshort}

[#pr-velero-backup-prepare]
==== Step 1: Preparing the registry

Before you create a backup, record the information that you need for a later restore.
Then stop the tasks that could change registry data while the backup runs.
Replace `<PRIVATE_REGISTRY_NAMESPACE>` with the namespace of your deployment and `<RELEASE_NAME>` with the name of your {helm} release.

. Save your {productnameshort} chart version, application version and {helm} values in a secure recovery record:
+
[source,bash,subs="+attributes"]
----
{prompt_user}helm list -n <PRIVATE_REGISTRY_NAMESPACE>
{prompt_user}helm get values <RELEASE_NAME> -n <PRIVATE_REGISTRY_NAMESPACE> \
  -o yaml > <VALUES_FILE>.yaml
----
+
[NOTE]
====
The `-o yaml` option is required.
Without it, `helm get values` prints a `USER-SUPPLIED VALUES:` header, and the resulting file is not a valid values file.
====
+
If Fleet manages the release, also record the Git repository, revision, path, target cluster and Fleet workspace.
Preserve the `fleet.yaml` configuration, chart version, release name, namespace and references to external values and secrets.
Protect the Fleet management configuration separately from the {productnameshort} namespace backup.
. Record your namespace, release name, persistent volume claim (PVC) names, and storage classes. The following command only lists the PVCs in the namespace; it does not back up the PVC data or the storage configuration:
+
[source,bash,subs="+attributes"]
----
{prompt_user}kubectl get pvc -n <PRIVATE_REGISTRY_NAMESPACE>
----
. Record your TLS, OIDC, image-pull, and database secret references. The following command only lists the existing secrets in the namespace; it does not back up the secrets or their values:
+
[source,bash,subs="+attributes"]
----
{prompt_user}kubectl get secrets -n <PRIVATE_REGISTRY_NAMESPACE>
----
. Enable *Repository Read Only* in the {productnameshort} administrator interface.
. Stop or postpone image pushes, chart pushes, garbage collection, replication, and security scans.

[#pr-velero-backup-exclude-redis]
==== Step 2: Excluding {redis}

{redis} is not part of the backup target because it mainly contains user session and cache data.
Exclude it from the backup so that the restored environment does not contain stale session state.

. Identify the {redis} resources of your release:
+
[source,bash,subs="+attributes"]
----
{prompt_user}kubectl get sts,pod -n <PRIVATE_REGISTRY_NAMESPACE> -l component=redis
----
+
The {redis} PVC is created from a volume claim template and does not carry the `component` label, so it cannot be selected by label.
Its name is always `data-<RELEASE_NAME>-harbor-redis-0`.
. Exclude the {redis} pod, PVC, and persistent volume (PV) from the backup:
+
[source,bash,subs="+attributes"]
----
{prompt_user}kubectl label pod -n <PRIVATE_REGISTRY_NAMESPACE> -l component=redis \
  velero.io/exclude-from-backup=true --overwrite
{prompt_user}kubectl label pvc -n <PRIVATE_REGISTRY_NAMESPACE> \
  data-<RELEASE_NAME>-harbor-redis-0 velero.io/exclude-from-backup=true --overwrite
{prompt_user}kubectl label pv $(kubectl get pvc -n <PRIVATE_REGISTRY_NAMESPACE> \
  data-<RELEASE_NAME>-harbor-redis-0 -o jsonpath='{.spec.volumeName}') \
  velero.io/exclude-from-backup=true --overwrite
----

[WARNING]
====
Do not add the `velero.io/exclude-from-backup` label to the {redis} StatefulSet.
Excluding the StatefulSet removes the {redis} workload from the backup entirely.
After a restore, the cluster then has no {redis} deployment, and the core and job service pods fail repeatedly.
When only the pod, the PVC, and the PV are excluded, the StatefulSet is restored and creates an empty {redis} volume.
====

[#pr-velero-backup-create]
==== Step 3: Creating the backup

Use the backup method that matches your storage platform.
Replace `<BACKUP_NAME>` with a name for the backup and `<RETENTION_DURATION>` with the retention period, for example, `720h`.

*File System Backup*

File System Backup copies the volume content through the Velero node agent.
It does not depend on volume snapshot support in the storage provider, so it also works with storage backends such as `local-path`.

[NOTE]
====
If you use the Velero image from {sappco}, set `HOME` to `/scratch` in the Velero {helm} chart values file.
Without a writable `HOME`, File System Backup can fail with `mkdir /udmrepo: permission denied`.

[source,yaml]
----
configuration:
  extraEnvVars:
    - name: HOME
      value: /scratch
----
====
[source,bash,subs="+attributes"]
----
{prompt_user}velero backup create <BACKUP_NAME> \
  --include-namespaces <PRIVATE_REGISTRY_NAMESPACE> \
  --default-volumes-to-fs-backup \
  --ttl <RETENTION_DURATION> \
  --wait
----

*CSI volume snapshots*

If your storage platform supports CSI snapshots, use the snapshot-based approach instead.
It requires a CSI driver with snapshot support and a `VolumeSnapshotClass` that is labeled `velero.io/csi-volumesnapshot-class: "true"`.

[source,bash,subs="+attributes"]
----
{prompt_user}velero backup create <BACKUP_NAME> \
  --include-namespaces <PRIVATE_REGISTRY_NAMESPACE> \
  --snapshot-volumes \
  --ttl <RETENTION_DURATION> \
  --wait
----

[#pr-velero-backup-verify]
==== Step 4: Verifying the backup

A backup is not complete until you verify that the expected resources and volumes are included.

. Review the result and the volume coverage:
+
[source,bash,subs="+attributes"]
----
{prompt_user}velero backup describe <BACKUP_NAME> --details
----
. Confirm that the phase is `Completed`, and that the registry PVC, the {postgresql} PVC, and the job service PVC are included in the backup.
. Confirm that no {redis} volume is listed in the backup:
+
[source,bash,subs="+attributes"]
----
{prompt_user}kubectl -n velero get podvolumebackups \
  -l velero.io/backup-name=<BACKUP_NAME> \
  -o custom-columns='POD:.spec.pod.name,VOLUME:.spec.volume,PHASE:.status.phase'
----
. Disable *Repository Read Only* after the backup completes successfully.

[#pr-velero-schedule]
=== Automating backups

You can automate {productnameshort} backups with Velero schedules.
A schedule creates periodic backups based on a standard cron expression, which provides consistent recovery points without manual intervention.

. Verify that the {redis} pod, PVC, and PV are still labeled with `velero.io/exclude-from-backup=true`:
+
[source,bash,subs="+attributes"]
----
{prompt_user}kubectl get pod,pvc -n <PRIVATE_REGISTRY_NAMESPACE> \
  -l velero.io/exclude-from-backup=true
----
+
[NOTE]
====
The label on a pod is lost when the pod is recreated, for example, after an upgrade or a node restart.
Check the {redis} pod label again after any operation that recreates the pod.
The labels on the PVC and the PV persist.
====
. Create a schedule that uses the same backup method as your manual backup. For example, to run a File System Backup every day at 2:00 AM:
+
[source,bash,subs="+attributes"]
----
{prompt_user}velero schedule create <SCHEDULE_NAME> \
  --schedule="0 2 * * *" \
  --include-namespaces <PRIVATE_REGISTRY_NAMESPACE> \
  --default-volumes-to-fs-backup \
  --ttl <RETENTION_DURATION>
----
+
If you back up with CSI snapshots, replace `--default-volumes-to-fs-backup` with `--snapshot-volumes`.
. Verify that the schedule is active and configured correctly:
+
[source,bash,subs="+attributes"]
----
{prompt_user}velero schedule get <SCHEDULE_NAME>
----

[#pr-velero-restore]
=== Restoring {productnameshort}

If Fleet manages the deployment, read xref:pr-velero-restore-fleet[] before restoring.
The {productnameshort} namespace backup does not restore the Fleet management configuration.

[IMPORTANT]
====
During a File System Backup restore, Velero adds an init container to restored pods in the registry namespace.
This container uses the Velero image from {sappco}.
That namespace does not contain the {sappco} pull secret, so the nodes of the recovery cluster must be able to pull the image themselves.
Otherwise, the restored pods remain in the `ImagePullBackOff` state and the volume data is not restored.
Before you restore, configure the {sappco} credentials in the container runtime of every node.
For example, on {rke2a}, add the following to `/etc/rancher/rke2/registries.yaml` on every node and restart the `rke2-server` or `rke2-agent` service.
Replace `<APPCO_USERNAME>` and `<APPCO_PASSWORD>` with your {sappco} credentials:

[source,yaml]
----
configs:
  dp.apps.rancher.io:
    auth:
      username: <APPCO_USERNAME>
      password: <APPCO_PASSWORD>
----
====

[#pr-velero-restore-internal-db]
==== Restoring a deployment with an internal {postgresql} database

Use this procedure when {postgresql} runs inside the {kube} cluster.
Velero recreates the namespace, the workloads, the PVCs, the secrets, and the {helm} release secret.
Therefore, do not install the chart before you restore.

[WARNING]
====
Do not run `helm install` before the restore.
Velero skips every resource that already exists.
A pre-created release therefore keeps the empty PVCs and the new secrets of the fresh installation, and the backed-up data is not restored.
A new installation also regenerates the `<RELEASE_NAME>-core` secret and the token CA, which invalidates all existing robot accounts.
====

. Provision the target {kube} cluster with the same `StorageClass` names as the source cluster, and install the required {ingress} and Velero components.
Configure Velero with the same `BackupStorageLocation` that holds the backup.
. Wait until the backup is visible in the target cluster before you restore it. If the backup is still synchronizing from the object store, `velero backup get` can report that it is unavailable or return `not found` until the object-store upload completes:
+
[source,bash,subs="+attributes"]
----
{prompt_user}velero backup get <BACKUP_NAME>
----
. Restore the backup:
+
[source,bash,subs="+attributes"]
----
{prompt_user}velero restore create <RESTORE_NAME> \
  --from-backup <BACKUP_NAME> \
  --wait
----
. Review the result and confirm that all items were restored:
+
[source,bash,subs="+attributes"]
----
{prompt_user}velero restore describe <RESTORE_NAME> --details
----
+
A warning about the `kube-root-ca.crt` ConfigMap that already exists is expected and can be ignored.
Warnings about PVCs, secrets, or workloads that already exist indicate that the namespace was not empty, and that the restore is incomplete.
. Confirm that the {helm} release is known again in the restored cluster:
+
[source,bash,subs="+attributes"]
----
{prompt_user}helm list -n <PRIVATE_REGISTRY_NAMESPACE>
----
. Verify that the TLS, OIDC, image-pull, and database secrets were restored.
Recreate only the secrets that are managed outside the namespace, such as certificates issued by an external certificate manager.
Do not recreate the secrets that the chart generates, because this invalidates the robot accounts of the registry.
. If the recovery cluster is reached at a different address than the source cluster, update `externalURL` and the {ingress} host.
For a Fleet-managed release, make these changes in the Fleet configuration instead of running a manual {helm} upgrade.
Otherwise, update the saved values file and upgrade the release with that file:
+
[source,bash,subs="+attributes"]
----
{prompt_user}helm upgrade <RELEASE_NAME> \
  oci://registry.suse.com/private-registry/<APP_VERSION>/private-registry-helm \
  --namespace <PRIVATE_REGISTRY_NAMESPACE> \
  --version <CHART_VERSION> \
  -f <VALUES_FILE>.yaml
----
If {ranchera} provides OIDC, update the `redirectURIs` entry in the `OIDCClient` resource.
See xref:pr-configure-rancher-oidc-create-client[].
. Perform the checks in xref:pr-velero-verification[].

[NOTE]
====
The chart version, the application version, and the values file that you saved in <<pr-velero-backup-prepare>> are a fallback for rebuilding the release manually.
They are not required for the restore itself.
====

[#pr-velero-restore-external-db]
==== Restoring a deployment with an external {postgresql} database

Use this procedure when your database and object storage are managed outside of the {kube} cluster.

. Provision the target {kube} cluster and the required Velero components, and configure Velero with the same `BackupStorageLocation` that holds the backup.
. Confirm that the backup is available in the target cluster before you start the restore:
+
[source,bash,subs="+attributes"]
----
{prompt_user}velero backup get <BACKUP_NAME>
----
. Restore the external {postgresql} database with the native recovery procedure of your database provider.
. Restore the external registry object-storage data with its native recovery procedure.
. Restore the {productnameshort} {kube} resources and the in-cluster PVCs into an empty namespace:
+
[source,bash,subs="+attributes"]
----
{prompt_user}velero restore create <RESTORE_NAME> \
  --from-backup <BACKUP_NAME> \
  --wait
----
. Verify that the connection secret of the external database and the TLS CA or OIDC credentials were restored, and recreate only the ones that are managed outside the namespace.
. Start the registry and verify that it connects to the restored database.
. Perform the checks in xref:pr-velero-verification[].

[#pr-velero-restore-fleet]
==== Restoring a Fleet-managed deployment

Fleet manages the desired deployment, while Velero restores the registry resources and volume data.
Coordinate both tools during recovery to prevent Fleet from creating empty claims before Velero restores the data.
Restoring the {helm} release alone does not establish that Fleet manages the deployment again.

The following procedure restores into a new cluster or an empty namespace.
Test it in a recovery environment with the Fleet and Velero versions used in production.

. Recover the Fleet management configuration.
Before connecting or targeting the recovery cluster, set `paused: true` in the bundle's `fleet.yaml` configuration.
Confirm that Fleet has applied the pause and that no deployment is in progress.
Pausing the bundle also affects its other target clusters.
Then connect the recovery cluster to Fleet.
See the link:https://documentation.suse.com/cloudnative/continuous-delivery/latest/en/reference/ref-fleet-yaml.html[Fleet configuration reference].
. Confirm that the target namespace contains no {productnameshort} release, PVCs or chart-generated secrets.
Do not install the chart through Fleet or {helm} before the restore.
Velero normally skips resources that already exist, including PVCs.
. Provision the required {ingress}, storage classes and Velero components on the target cluster.
Configure Velero with the backup storage location and verify that the backup is available:
+
[source,console,subs="+attributes"]
----
{prompt_user}velero backup get <BACKUP_NAME>
----
+
If you use an external {postgresql} database or external object storage, restore them with their provider procedures before starting the registry.
. Restore the namespace backup:
+
[source,console,subs="+attributes"]
----
{prompt_user}velero restore create <RESTORE_NAME> \
  --from-backup <BACKUP_NAME> \
  --wait
----
. Review `velero restore describe <RESTORE_NAME> --details`.
Verify that the expected PVCs and original secrets are restored and that the PVCs are bound.
For File System Backup, verify that the expected pod volume restores are complete.
Investigate warnings about existing resources and resolve restore errors before continuing.
. Configure the Fleet bundle to use the recovered release name, namespace, chart version and values.
Restore external values and secrets that Fleet requires.
If the address changes, update `externalURL` and the {ingress} host in the Fleet configuration.
If {ranchera} provides OIDC, update the `redirectURIs` entry in the `OIDCClient` resource.
See xref:pr-configure-rancher-oidc-create-client[].
Do not replace the chart-generated secrets with newly generated secrets.
+
[NOTE]
====
If the chart is hosted on an authenticated OCI registry, such as `registry.suse.com`, also restore the `helmSecretName` credential that the `GitRepo` uses to pull the chart.
This credential is separate from the {productnameshort} image-pull secret.
Create or restore the credential in the namespace of the `GitRepo`, not only in the {productnameshort} namespace.
See xref:pr-install-rancher-repository[] for the equivalent credential used when installing through the {ranchera} UI.
====
. Remove `paused: true` or set `paused: false` in the `fleet.yaml` configuration.
Commit and push the change to the Fleet Git source.
Wait for Fleet to reconcile the bundle and verify that its target deployment reaches the `Ready` state.
Check the GitRepo and bundle status in the Fleet workspace:
+
[source,console,subs="+attributes"]
----
{prompt_user}kubectl -n <FLEET_WORKSPACE_NAMESPACE> describe gitrepo <GITREPO_NAME>
{prompt_user}kubectl -n <FLEET_WORKSPACE_NAMESPACE> describe bundle <BUNDLE_NAME>
----
+
Confirm that the bundle targets the recovery cluster and reports the deployment as `Ready`.
If Fleet reports an ownership conflict or does not manage the restored release, investigate the Fleet status before making further changes.
Do not force ownership or reinstall the chart as a recovery shortcut.
. Perform the checks in xref:pr-velero-verification[].
In a test environment, also confirm that a subsequent Fleet configuration change reaches the recovered deployment.

[NOTE]
====
For existing PVCs, an in-place restore is available only with supported Velero versions and backup methods.
The documented CSI snapshot method without data movement does not support this option.
Pause Fleet, stop access to the target volumes and back them up before an in-place restore.
File System Backup requires additional workload preparation and restored pods; restoring PVC objects alone does not restore their data.
See the link:https://velero.io/docs/latest/volume-data-inplace-restore/[Velero in-place restore documentation] for the latest stable version.
Select the documentation for your Velero version before using this method.
====

[#pr-velero-verification]
=== Verification and troubleshooting

After the restore, validate that the registry is fully operational.

. Check the PVCs and the pods, and confirm that the PVCs are bound and the pods are running:
+
[source,bash,subs="+attributes"]
----
{prompt_user}kubectl get pvc -n <PRIVATE_REGISTRY_NAMESPACE>
{prompt_user}kubectl get pods -n <PRIVATE_REGISTRY_NAMESPACE>
----
. Validate the API health, the administrator login and image pulls.
. Confirm that the projects, users and artifacts that existed at backup time are present again, and that a robot account can still authenticate.
. Disable *Repository Read Only*, then validate image pushes.

If the restore does not complete as expected, check the following:

* `velero restore describe <RESTORE_NAME> --details` reports resources that already exist.
Investigate the affected resources.
Existing PVCs, secrets or workloads can prevent a complete restore.
* PVCs remain `Pending`.
The `StorageClass` of the source cluster does not exist in the recovery cluster, or it cannot provision the requested volume.
* No volume data is restored.
The Velero node agent was not running when the backup was created, so no `PodVolumeBackup` was produced. Verify the backup with `velero backup describe <BACKUP_NAME> --details`.
* Velero cannot find the backup in the recovery cluster.
The `BackupStorageLocation` is not the one that holds the backup, or it is not in the `Available` phase. Check it with `kubectl -n velero get backupstoragelocation`.
* Users cannot log in, and robot accounts fail to authenticate.
The chart-generated secrets were recreated instead of restored.
