[#pr-migrating-from-harbor]
== Migrating data from upstream {harbor} to {productname}

:revdate: 2026-09-17
:page-revdate: {revdate}

[#pr-migrating-from-harbor-overview]
=== Overview

{productname} ({productnameshort}) is derived from {harbor} and shares the same PostgreSQL database schema and registry blob storage layout.
This means that data from an existing Harbor installation, including projects, users, repositories, artefacts, robot accounts, policies and image/chart blobs, can be migrated to {productnameshort} using a database dump/restore and a copy of the registry blob storage. This avoids the need to re-push every artefact manually.
§
This guide covers migrating:

* The {harbor} PostgreSQL database (all metadata: projects, users, repositories, artifacts, tags, policies, etc.)
* The registry blob storage (the actual image layers and {helm} chart content)

It does not cover the migration of Harbor's configuration itself (e.g. auth backends, replication endpoints and quotas). Review your existing Harbor Helm values and reapply the relevant settings to your {productnameshort} installation separately.

[#pr-migrating-from-harbor-prerequisites]
=== Prerequisites

* `kubectl` access to the namespace(s) hosting both the source {harbor} installation and the destination {productnameshort} installation (the same cluster or different clusters both work, as long as your `kubectl` context can reach whichever side you're operating on at each step).
* Enough local (or otherwise accessible) disk space to hold the database dump and the registry blob archive -- size the blob archive against your {harbor} registry's actual storage usage.
* A destination PostgreSQL major version equal to or newer than the source. Both {harbor} and {productnameshort} bundle PostgreSQL, so this is normally satisfied automatically, but confirm it if either side uses an external/managed database.
* A cluster that supports ephemeral debug containers (`kubectl debug`, GA since {kube} 1.25). This is required to work around a specific {productnameshort} limitation described in <<pr-migrating-from-harbor-restore>>.
* If your cluster enforces the `restricted` Pod Security Standard, plan for a temporary exception: the debug container used in <<pr-migrating-from-harbor-restore>> needs `runAsUser: 0` and the `SYS_PTRACE` capability. Loosening the namespace's Pod Security label for the duration of the migration (or using an equivalent exemption) is the simplest approach.
* A maintenance window. Both the source {harbor} and the destination {productnameshort} are put into a read-only/quiesced state (and briefly scaled down) while data is copied, so clients cannot push during the migration.

[WARNING]
====
Take a full backup or storage snapshot of both the source {harbor} and destination {productnameshort} independently of the export this procedure produces. The steps below are destructive to the {productnameshort} database and registry storage -- they overwrite both.
====

[#pr-migrating-from-harbor-export]
=== Step 1: Export data from {harbor}

Set variables for your environment:

[source,bash,subs="+attributes"]
----
SRC_NAMESPACE=<harbor-namespace>
SRC_HOST=<harbor-external-hostname>
SRC_ADMIN_PASSWORD=<harbor-admin-password>
EXPORT_PATH=./harbor-export-$(date +%Y%m%d-%H%M%S)
{prompt_user}mkdir -p "$EXPORT_PATH"

SRC_DB_POD=$(kubectl -n "$SRC_NAMESPACE" get pod -l component=database -o jsonpath='{.items[0].metadata.name}')
SRC_REGISTRY_POD=$(kubectl -n "$SRC_NAMESPACE" get pod -l component=registry -o jsonpath='{.items[0].metadata.name}')
----

Put {harbor} into read-only mode so no new writes land during the export:

[source,bash,subs="+attributes"]
----
{prompt_user}curl -sk -u "admin:${SRC_ADMIN_PASSWORD}" \
  -H 'Content-Type: application/json' \
  -X PUT "https://${SRC_HOST}/api/v2.0/configurations" \
  -d '{"read_only":true}'
----

Scale down the components that could still write to the database or registry storage in the background (job execution, vulnerability scanning). Leave `core`, `registry`, and `database` running -- they're needed to serve the export itself:

[source,bash,subs="+attributes"]
----
{prompt_user}kubectl -n "$SRC_NAMESPACE" scale deploy -l component=jobservice --replicas=0
{prompt_user}kubectl -n "$SRC_NAMESPACE" scale deploy -l component=trivy --replicas=0
----

Dump the database:

[source,bash,subs="+attributes"]
----
{prompt_user}kubectl -n "$SRC_NAMESPACE" exec "$SRC_DB_POD" -- pg_dump -U postgres -d registry \
  > "${EXPORT_PATH}/harbor-db.sql"
----

Archive the registry blob storage:

[source,bash,subs="+attributes"]
----
{prompt_user}kubectl -n "$SRC_NAMESPACE" exec "$SRC_REGISTRY_POD" -c registry -- \
  tar czf - -C /storage . > "${EXPORT_PATH}/harbor-registry-blobs.tgz"
----

Confirm both exports are non-empty before continuing:

[source,bash,subs="+attributes"]
----
{prompt_user}[ -s "${EXPORT_PATH}/harbor-db.sql" ] && [ -s "${EXPORT_PATH}/harbor-registry-blobs.tgz" ] \
  && echo "Export looks good" || echo "ERROR: export incomplete"
----

Keep `$EXPORT_PATH` until the migration is verified in <<pr-migrating-from-harbor-verify>> -- do not delete it after decommissioning {harbor}.

[#pr-migrating-from-harbor-decommission]
=== Step 2: Decommission the source {harbor}

Once you have confirmed that the above export files are present and not empty, keep the source {harbor} deployment available until the migrated {productname} instance is running correctly with the restored data. If something goes wrong during verification, you can restore the old registry from the export instead of losing access to the source data. You can keep the source deployment scaled down or read-only as long as you're not ready to remove it completely. Just make sure that it's not accepting any writes that the migrated instance won't see.

[#pr-migrating-from-harbor-prepare-spr]
=== Step 3: Install or prepare {productname}

Install {productnameshort} following the standard installation procedure described in <<pr-deployment>>. Two choices matter specifically for a smooth migration:

External hostname::
Configure {productnameshort} with the same external URL/hostname the source {harbor} used. This keeps existing client logins, robot account credentials, CI pipeline configuration, and pull secrets working without changes after the cutover. If you must change the hostname, plan a separate client-side update.

Persistent storage::
Provision enough storage for the restored registry blobs plus headroom for future growth, sized against the blob archive produced in <<pr-migrating-from-harbor-export>>.

Do not seed {productnameshort} with production traffic yet -- the restore in the next step overwrites its database and registry storage.

[#pr-migrating-from-harbor-restore]
=== Step 4: Restore the data into {productnameshort}

Set variables for the destination:

[source,bash,subs="+attributes"]
----
DST_NAMESPACE=<spr-namespace>
DST_DB_POD=$(kubectl -n "$DST_NAMESPACE" get pod -l component=database -o jsonpath='{.items[0].metadata.name}')
DST_REGISTRY_POD=$(kubectl -n "$DST_NAMESPACE" get pod -l component=registry -o jsonpath='{.items[0].metadata.name}')
----

Scale down the components that write to or read from the database -- but leave `registry` running, since the blob-restore step below needs the registry pod alive to copy files into it:

[source,bash,subs="+attributes"]
----
{prompt_user}kubectl -n "$DST_NAMESPACE" scale deploy -l component=core --replicas=0
{prompt_user}kubectl -n "$DST_NAMESPACE" scale deploy -l component=jobservice --replicas=0
{prompt_user}kubectl -n "$DST_NAMESPACE" scale deploy -l component=trivy --replicas=0
{prompt_user}kubectl -n "$DST_NAMESPACE" wait --for=delete pod -l component=core --timeout=120s
----

[#pr-migrating-from-harbor-restore-database]
==== Restore the database

[source,bash,subs="+attributes"]
----
{prompt_user}kubectl -n "$DST_NAMESPACE" cp "${EXPORT_PATH}/harbor-db.sql" "${DST_DB_POD}:/tmp/harbor-db.sql"
{prompt_user}kubectl -n "$DST_NAMESPACE" exec "$DST_DB_POD" -- \
  psql -U postgres -d registry -c 'DROP SCHEMA public CASCADE; CREATE SCHEMA public;'
{prompt_user}kubectl -n "$DST_NAMESPACE" exec "$DST_DB_POD" -- \
  psql -v ON_ERROR_STOP=1 -U postgres -d registry -f /tmp/harbor-db.sql
{prompt_user}kubectl -n "$DST_NAMESPACE" exec "$DST_DB_POD" -- rm -f /tmp/harbor-db.sql
----

[#pr-migrating-from-harbor-restore-blobs]
==== Restore the registry blobs

[IMPORTANT]
====
{productnameshort}'s `registry` container image does not include a `tar` binary. A plain `kubectl cp` or `kubectl exec ... tar` against it fails -- `kubectl cp` itself relies on `tar` being present in the target container for both directions of the copy. (Upstream {harbor}'s registry image does have `tar`, which is why it works fine for the export in <<pr-migrating-from-harbor-export>> -- this limitation is specific to restoring *into* {productnameshort}.)
====

Work around this by attaching an ephemeral debug container -- one that does have `tar` -- to the registry pod, sharing its process namespace. From there, the registry container's filesystem is reachable through `/proc/<pid>/root`:

[source,bash,subs="+attributes"]
----
{prompt_user}cat > /tmp/debug-profile.json <<'EOF'
{
  "securityContext": {
    "runAsUser": 0,
    "runAsNonRoot": false,
    "capabilities": { "add": ["SYS_PTRACE"] }
  }
}
EOF

{prompt_user}kubectl -n "$DST_NAMESPACE" debug "$DST_REGISTRY_POD" -c restore-helper \
  --image=registry.suse.com/bci/bci-busybox:16.0 \
  --target=registry --custom=/tmp/debug-profile.json -- sleep 600
----

Wait for the debug container to be running, then locate the registry process's PID from inside it:

[source,bash,subs="+attributes"]
----
{prompt_user}kubectl -n "$DST_NAMESPACE" wait --for=jsonpath='{.status.ephemeralContainerStatuses[?(@.name=="restore-helper")].state.running}' \
  pod/"$DST_REGISTRY_POD" --timeout=60s

REGISTRY_PID=$(kubectl -n "$DST_NAMESPACE" exec "$DST_REGISTRY_POD" -c restore-helper -- sh -c '
  for p in /proc/[0-9]*; do
    if tr "\0" " " < "$p/cmdline" 2>/dev/null | grep -q "^registry serve"; then
      basename "$p"; break
    fi
  done
')
----

Copy the blob archive in and extract it into the registry's storage path through the debug container:

[source,bash,subs="+attributes"]
----
{prompt_user}kubectl -n "$DST_NAMESPACE" cp "${EXPORT_PATH}/harbor-registry-blobs.tgz" \
  "${DST_REGISTRY_POD}:/tmp/harbor-registry-blobs.tgz" -c restore-helper

{prompt_user}kubectl -n "$DST_NAMESPACE" exec "$DST_REGISTRY_POD" -c restore-helper -- sh -c \
  "rm -rf /proc/${REGISTRY_PID}/root/storage/* && \
   tar xzf /tmp/harbor-registry-blobs.tgz -C /proc/${REGISTRY_PID}/root/storage && \
   rm -f /tmp/harbor-registry-blobs.tgz"
----

Restart the registry deployment so it picks up the restored files with a clean process (this also clears the temporary debug container):

[source,bash,subs="+attributes"]
----
{prompt_user}kubectl -n "$DST_NAMESPACE" rollout restart deploy -l component=registry
{prompt_user}kubectl -n "$DST_NAMESPACE" rollout status deploy -l component=registry --timeout=180s
----

[#pr-migrating-from-harbor-restore-bring-up]
==== Bring the rest of {productnameshort} back up

[source,bash,subs="+attributes"]
----
{prompt_user}kubectl -n "$DST_NAMESPACE" scale deploy -l component=core --replicas=1
{prompt_user}kubectl -n "$DST_NAMESPACE" scale deploy -l component=jobservice --replicas=1
{prompt_user}kubectl -n "$DST_NAMESPACE" scale deploy -l component=trivy --replicas=1
{prompt_user}kubectl -n "$DST_NAMESPACE" rollout status deploy -l component=core --timeout=180s
----

[#pr-migrating-from-harbor-verify]
=== Step 5: Verify the migration

Check {productnameshort}'s health endpoint:

[source,bash,subs="+attributes"]
----
{prompt_user}curl -sk -u admin:<spr-admin-password> "https://<spr-host>/api/v2.0/health"
----

Confirm known data survived by querying the API for a project, its repositories/artifacts, and a known user, substituting values you expect to exist:

[source,bash,subs="+attributes"]
----
{prompt_user}curl -sk -u admin:<spr-admin-password> "https://<spr-host>/api/v2.0/projects/<project-name>"
{prompt_user}curl -sk -u admin:<spr-admin-password> \
  "https://<spr-host>/api/v2.0/projects/<project-name>/repositories/<repo-name>/artifacts/<tag>"
{prompt_user}curl -sk -u admin:<spr-admin-password> "https://<spr-host>/api/v2.0/users?username=<username>"
----

API checks only confirm the database rows migrated. To confirm the blob data itself is intact, do a real pull-back of a known image and/or {helm} chart:

[source,bash,subs="+attributes"]
----
{prompt_user}docker pull <spr-host>/<project-name>/<repo-name>:<tag>
{prompt_user}helm pull oci://<spr-host>/<project-name>/<chart-name> --version <chart-version>
----

A successful pull with the expected digest is the strongest confirmation that the migration succeeded end-to-end.

[#pr-migrating-from-harbor-rollback]
=== Rollback

If verification fails, don't discard the {harbor} export. Reinstall {harbor} (or resume the instance left scaled down in <<pr-migrating-from-harbor-decommission>>) and resume serving traffic from it while you investigate, then retry the {productnameshort} restore from the same export once the issue is resolved.
