[#observability-integration]
== Integrating {sobservability} with {productname}

This chapter installs {productname} and {sobservability} on an existing {kube} cluster, then connects {productname} through the agent telemetry gateway.

For a fresh installation, follow xref:pr-observability-preflight[], xref:pr-observability-https-ingress[], and xref:pr-observability-fresh-install[], then continue with the numbered integration steps.
If {productname} is already installed, start with xref:pr-observability-existing-install[] instead.

[#pr-observability-quick-overview]
=== What will this chapter accomplish? (5-minute read)

By the end, you will have:

. *{sobservability} backend installed* — Dashboards, alerting, telemetry storage
. *Agent deployed* — Collects {kube} cluster telemetry
. *{productname} tracing enabled* — {harbor} sends traces to {sobservability}
. *Observability dashboard created* — View {productname} metrics and traces

This chapter does *not* cover:
* Production-grade high-availability setup (see {sobservability} documentation)
* Using {sobservability} for non-{harbor} workloads
* Custom dashboard creation (template provided; modify as needed)

.Choose your path:

[#pr-observability-checklist]
=== Before you start: Quick checklist

Verify you have all these items ready before proceeding.

* ✅ Valid {sobservability} trial or subscription license (contact SUSE)
* ✅ {kube} cluster with version supported by {sobservability} charts
* ✅ Administrator access to create namespaces, {kube} secrets, and cluster roles
* ✅ Persistent volume provisioner enabled in your cluster
* ✅ {helm} 3.x installed locally
* ✅ `kubectl` configured with cluster credentials
* ✅ 7.2 CPU cores and 23.4 GiB RAM available (for backend)
* ✅ Network access from {harbor} to telemetry gateway

If you are missing any items, see xref:pr-observability-prerequisites[] for details.

[TIP]
====
Experienced users: Jump to xref:pr-observability-existing-install[] if {productname} is already running.
====

The examples in this chapter assume an existing k3d cluster using Traefik as the ingress controller.
Substitute your own cluster name and storage class wherever this chapter sets `CLUSTER_NAME` or uses `REPLACE_WITH_STORAGE_CLASS`.
They also use these local test host names, not public DNS records:

* {productname}: `core.harbor.domain`
* {sobservability}: `observability.example.com`

[#pr-observability-versions]
=== Versions and architecture

This chapter uses {productname} chart `1.1.29` (application `1.1.3`), {sobservability} backend `2.12.0`, and agent `1.7.19`, deployed on a two-node k3d cluster.
{productname} uses Traefik and chart-generated TLS (`expose.tls.certSource: auto`); {sobservability} uses a certificate signed by a local test CA.
They therefore have different certificate trust requirements, and no host trust settings need to change.

Counters, timestamps, IDs, and graph values shown in this chapter's screenshots are examples, not fixed values you should expect to reproduce exactly.
xref:pr-observability-existing-install[] only covers a same-chart integration update, not a production chart migration.
This procedure does not cover every {kube} version, and does not guarantee long-term process-agent stability on shared-kernel k3d nodes; see xref:pr-observability-busy-kprobes[] for a known limitation.

For the alternative standalone OpenTelemetry Collector and Jaeger setup, see the `OpenTelemetry` example configuration kept alongside this chapter's working files.
The {otelemetry} settings in this chapter remain here because they configure the {sobservability} integration, not the standalone collector.

The commands in this chapter run from the repository root and use these component versions:

[#pr-observability-data-flow]
=== Data flow

[source,text]
----
Harbor core, jobservice, and registryctl
  -> OTLP/HTTP gateway on port 4318, path /v1/traces
  -> SUSE Observability backend
  -> Trace Explorer
----

This enables traces for these {harbor} components, not automatic instrumentation of every container.
The agent separately collects {kube} telemetry.
Installing the backend alone does not enable {productname} tracing.

[#pr-observability-prerequisites]
=== Prerequisites

* A valid {sobservability} trial or subscription license.
* {kube} and {helm} versions supported by the selected {sobservability} charts.
* Permissions to create namespaces, workloads, Secrets, ClusterRoles, and ClusterRoleBindings. The node agent requires privileged workload permissions.
* A working persistent volume provisioner and access to `registry.rancher.com`.
* Access to the {productname} chart and SUSE registry images; for an existing release, access to the exact installed chart version.
* Network access from {harbor} to the gateway and from the gateway to the backend.

The documented trial backend requests approximately 7.2 CPU, 23.4 GiB RAM, and 154 GiB storage, in addition to existing workloads and agent resources.
Confirm the requirements for the selected chart version.
k3d nodes share host resources: do not count their reported CPU and memory as independent host capacity.

The examples in this chapter use the `trial` sizing profile, your cluster's storage class, HTTPS UI access, and HTTP in-cluster telemetry.
*This is an example configuration for testing, not production.*

Production deployments require:

* Appropriate cluster sizing (CPU, memory, persistent disk)
* Durable persistent storage with backup
* TLS certificates and access controls
* Data retention and backup policies
* High-availability configuration across multiple nodes

[#pr-observability-preflight]
=== Checking the existing cluster

Run the Bash examples from the workspace root.
Set the context explicitly in every terminal before using the remaining commands; {helm} and `kubectl` both honor `KUBECONFIG`.

[source,bash,subs="+attributes"]
----
# Replace with your own k3d cluster name.
CLUSTER_NAME=rancher-cluster
export KUBE_CONTEXT="k3d-$CLUSTER_NAME"
{prompt_user}kubectl --context "$KUBE_CONTEXT" get nodes
{prompt_user}helm --kube-context "$KUBE_CONTEXT" list -A
{prompt_user}kubectl --context "$KUBE_CONTEXT" get ingressclass,storageclass
{prompt_user}kubectl --context "$KUBE_CONTEXT" get ingress -A
{prompt_user}docker port "k3d-$CLUSTER_NAME-serverlb"
{prompt_user}free -h
{prompt_user}df -h /var/lib/docker
----

These commands show the cluster's node versions, {ingress} class, storage class, and host port mappings.
For example, you might see two Ready nodes running `v1.35.5+k3s1`, the `traefik` {ingress} class, default `local-path` storage, and host ports 80/443 mapped to the k3d load balancer.
Rancher and cert-manager may already be installed; check whether {productname} and {sobservability} releases already exist, and watch for old {productname} PVCs left over from a previous installation.

[NOTE]
====
Absence of a {helm} release does not mean that its database is empty.
Inspect `kubectl get pvc -n suse-registry` before a fresh install.
Check the charts' supported {kube} versions before applying them to a newer cluster.
====

Use the context flags shown above with every cluster command in this chapter, or create a private, context-specific kubeconfig before proceeding:

[source,bash,subs="+attributes"]
----
{prompt_user}umask 077
PRIVATE_DIR="$HOME/.config/spr-observability/$CLUSTER_NAME"
{prompt_user}mkdir -p "$PRIVATE_DIR"
{prompt_user}kubectl --context "$KUBE_CONTEXT" config view --minify --flatten --raw \
  > "$PRIVATE_DIR/kubeconfig"
export KUBECONFIG="$PRIVATE_DIR/kubeconfig"
OBSERVABILITY_DIR="$PWD/observability"
BACKEND_VALUES="$PRIVATE_DIR/backend-values.yaml"
AGENT_VALUES="$PRIVATE_DIR/agent-values.yaml"
SPR_INSTALL_VALUES="$PRIVATE_DIR/spr-install-values.yaml"
SPR_VALUES="$OBSERVABILITY_DIR/spr-otel.yml"
# Replace these with your own backend and agent release and namespace names.
OBSERVABILITY_RELEASE=suse-observability
OBSERVABILITY_NAMESPACE=suse-observability
AGENT_RELEASE=suse-observability-agent
AGENT_NAMESPACE=suse-observability-agent
----

[IMPORTANT]
====
Keep this directory private: the kubeconfig, {helm} value backups, and keys may contain credentials.
Do not add it to version control.
The commands in this chapter assume these variables and `KUBECONFIG` remain set; set them again in each new terminal.
Do not sum node-reported memory: both k3d nodes share the same host.
Stop if host capacity or {ingress} prerequisites fail; do not recreate the cluster or disturb its existing Rancher installation.
====

[#pr-observability-https-ingress]
=== Preparing HTTPS ingress

For an existing {productname} release, preserve its current host name and TLS configuration.
The fresh-installation example in xref:pr-observability-fresh-install[] uses chart-generated TLS, so prepare only the {sobservability} certificate here.
Its CA does not establish trust for {productname}'s separate, auto-generated certificate.

Generate a local test CA and SAN-bearing certificates.
Run this only once in a new private directory, and retain the CA for subsequent deployments rather than overwriting certificates that existing clients already trust.

[source,bash,subs="+attributes"]
----
{prompt_user}if [[ -e "$PRIVATE_DIR/ca.key" || -e "$PRIVATE_DIR/ca.crt" ]]; then
  printf 'Existing CA found: reuse it; do not run CA generation again.\n' >&2
  exit 1
fi
{prompt_user}openssl req -x509 -newkey rsa:3072 -nodes -days 365 \
  -keyout "$PRIVATE_DIR/ca.key" -out "$PRIVATE_DIR/ca.crt" \
  -subj '/CN=SPR Observability Local Test CA' \
  -addext 'basicConstraints=critical,CA:TRUE' \
  -addext 'keyUsage=critical,keyCertSign,cRLSign'
{prompt_user}for host in observability.example.com; do
  openssl req -new -newkey rsa:2048 -nodes \
    -keyout "$PRIVATE_DIR/$host.key" -out "$PRIVATE_DIR/$host.csr" \
    -subj "/CN=$host"
  openssl x509 -req -in "$PRIVATE_DIR/$host.csr" \
    -CA "$PRIVATE_DIR/ca.crt" -CAkey "$PRIVATE_DIR/ca.key" -CAcreateserial \
    -days 90 -out "$PRIVATE_DIR/$host.crt" \
    -extfile <(printf 'subjectAltName=DNS:%s\nextendedKeyUsage=serverAuth\n' "$host")
done
{prompt_user}kubectl create namespace suse-registry --dry-run=client -o yaml | kubectl apply -f -
{prompt_user}kubectl create namespace "$OBSERVABILITY_NAMESPACE" --dry-run=client -o yaml | kubectl apply -f -
{prompt_user}kubectl create secret tls observability-ingress-tls -n "$OBSERVABILITY_NAMESPACE" \
  --cert="$PRIVATE_DIR/observability.example.com.crt" \
  --key="$PRIVATE_DIR/observability.example.com.key" \
  --dry-run=client -o yaml | kubectl apply -f -
----

Add the following entry to the workstation's `/etc/hosts` using your normal administrative procedure.
Use the actual {ingress} address instead of `127.0.0.1` if the browser runs on another machine:

[source,text]
----
127.0.0.1 core.harbor.domain observability.example.com
----

[IMPORTANT]
====
Import *only* `ca.crt`, never `ca.key`, into the browser's trusted certificate authorities for {sobservability}.
For its `curl` checks, use `--cacert "$PRIVATE_DIR/ca.crt"`.
For {productname}, export its active public certificate after installation as shown in xref:pr-observability-fresh-install[].
Docker clients require {productname}'s trust certificate at `/etc/docker/certs.d/core.harbor.domain/ca.crt`; node container runtimes need their own trust configuration if they pull images from {productname}.
Host trust changes need administrator approval.
Do not restart {docker} without planning for the disruption to all k3d nodes.
Do not use `curl -k` or an insecure-registry exception as proof that HTTPS is configured correctly.
====

In the private backend values file used in xref:pr-observability-prepare-config[], use this {ingress} configuration (verified against chart `2.12.0` with `helm show values`):

[source,yaml]
----
global:
  imageRegistry: registry.rancher.com
  storageClass: REPLACE_WITH_STORAGE_CLASS
  suseObservability:
    license: REPLACE_WITH_VALID_LICENSE
    baseUrl: https://observability.example.com
    sizing:
      profile: trial
    adminPassword: REPLACE_WITH_STRONG_OBSERVABILITY_ADMIN_PASSWORD
ingress:
  enabled: true
  ingressClassName: traefik
  hosts:
    - host: observability.example.com
  tls:
    - secretName: observability-ingress-tls
      hosts:
        - observability.example.com
----

Keep the agent receiver URL internal, as shown in xref:pr-observability-install-agent[].
HTTPS {ingress} does not require changing the internal HTTP router or the OTLP gateway connection.

[#pr-observability-fresh-install]
=== Installing {productname} on a fresh cluster

Skip this section if {productname} is already installed; continue instead with xref:pr-observability-existing-install[].
Create the private file `$SPR_INSTALL_VALUES` in your editor with:

[source,yaml]
----
externalURL: https://core.harbor.domain/
harborAdminPassword: REPLACE_WITH_SEPARATE_SPR_ADMIN_PASSWORD
expose:
  type: ingress
  tls:
    enabled: true
    certSource: auto
  ingress:
    className: traefik
    hosts:
      core: core.harbor.domain
persistence:
  enabled: true
trace:
  enabled: false
----

Use your SCC mirroring credentials to authenticate the {helm} OCI registry and create the namespace-local image pull secret named `suse-registry`.
{helm} login and {kube} image authentication are separate.
A protected Docker auth file containing the credentials can be supplied without putting passwords on the command line:

[source,bash,subs="+attributes"]
----
# Authenticate using your normal secret-management workflow first.
# REGISTRY_AUTH_FILE must name a protected Docker-format auth JSON file.
{prompt_user}test -s "${REGISTRY_AUTH_FILE:?Set the path to your private registry auth JSON}"
{prompt_user}kubectl create secret generic suse-registry -n suse-registry \
  --type=kubernetes.io/dockerconfigjson \
  --from-file=.dockerconfigjson="$REGISTRY_AUTH_FILE" \
  --dry-run=client -o yaml | kubectl apply -f -
{prompt_user}helm show chart oci://registry.suse.com/private-registry/private-registry-helm \
  --version 1.1.29
{prompt_user}helm template spr oci://registry.suse.com/private-registry/private-registry-helm \
  --version 1.1.29 --namespace suse-registry \
  -f "$SPR_INSTALL_VALUES" > /dev/null
{prompt_user}helm install spr oci://registry.suse.com/private-registry/private-registry-helm \
  --version 1.1.29 --namespace suse-registry \
  -f "$SPR_INSTALL_VALUES" --wait --timeout 15m
{prompt_user}kubectl get pods,pvc,ingress -n suse-registry
{prompt_user}mkdir -p "$PRIVATE_DIR/spr-trust"
SPR_TLS_SECRET=$(kubectl get ingress spr-harbor-ingress -n suse-registry \
  -o jsonpath='{.spec.tls[0].secretName}')
{prompt_user}kubectl get secret "$SPR_TLS_SECRET" -n suse-registry \
  -o go-template='{{index .data "tls.crt"}}' | base64 --decode \
  > "$PRIVATE_DIR/spr-trust/ca.crt"
{prompt_user}curl --fail --cacert "$PRIVATE_DIR/spr-trust/ca.crt" \
  --resolve core.harbor.domain:443:127.0.0.1 \
  https://core.harbor.domain/api/v2.0/ping
----

[NOTE]
====
A Docker config containing only credential-helper references cannot supply a {kube} image pull secret: use an auth JSON with usable registry credentials.
Never display its contents in terminal captures.
====

Open {productname} over HTTPS and verify login before continuing to backend installation.
Tracing stays disabled until the gateway is ready.
Exporting the active public certificate does not export the private key.
Refresh client trust if a reinstall or chart update generates a new certificate; browser trust must also match this certificate, not the {sobservability} CA.

`spr-traefik-otel.yml` is the local combined tracing and Traefik override for a fresh installation.
It sets `certSource: auto`, the core host name, and `externalURL: https://core.harbor.domain/`.

[IMPORTANT]
====
`spr-traefik-otel.yml` may contain a local admin password: do not commit it or print it into screenshots.
For a new deployment, use a protected deployment copy and your own password.
For an existing release, use the tracing-only `spr-otel.yml` instead, unless you intentionally want to change its {ingress} and TLS too.
====

[#pr-observability-existing-install]
=== Using an existing {productname} installation

[WARNING]
====
Do not run the fresh-installation procedure in xref:pr-observability-fresh-install[] or overwrite {productname}'s {ingress} certificates.
====

Discover the actual release name, namespace, and chart version, then record its revision and private values before making any change:

[source,bash,subs="+attributes"]
----
{prompt_user}helm list -A
# Replace these with the existing release's actual identifiers.
SPR_RELEASE=spr
SPR_NAMESPACE=suse-registry
SPR_CHART_VERSION=1.1.29
{prompt_user}helm history "$SPR_RELEASE" -n "$SPR_NAMESPACE"
{prompt_user}helm get values "$SPR_RELEASE" -n "$SPR_NAMESPACE" \
  > "$PRIVATE_DIR/spr-before-values.yaml"
----

Record the current revision separately for rollback.
Verify that the exact installed chart supports `trace` and `metrics.serviceMonitor`; stop for a separately planned chart upgrade if it does not.
Install {sobservability} and its agent using xref:pr-observability-prepare-config[] through xref:pr-observability-install-agent[], then use xref:pr-observability-enable-tracing[] and xref:pr-observability-harbor-metrics[] with *the existing release, namespace, and pinned chart version*.
Preserve passwords, the external URL, certificates, PVCs, databases, and existing projects.
`--reuse-values` keeps existing configuration, but it does not replace a database or artifact backup.

Use integration-only overlays; do not pass fresh-install values to an existing release.
If your namespace differs, adjust `trace.namespace` and the monitoring verification paths too.
Verify existing image pull and push operations before and after the change.
To revert a failed configuration rollout:

[source,bash,subs="+attributes"]
----
{prompt_user}helm rollback "$SPR_RELEASE" "${SPR_PREVIOUS_REVISION:?Set the recorded revision}" \
  -n "$SPR_NAMESPACE" --wait --timeout 15m
----

Rollback restores release configuration, not deleted or changed registry data.

[#pr-observability-clean-reinstall]
==== Optional: Performing a clean reinstall that deletes data

[WARNING]
====
This is *not* part of the existing-installation integration path.
Uninstalling {helm} normally retains {productname} PVCs, including its database.
Setting `harborAdminPassword` during reinstall does not reset an initialized database's administrator password; this was the cause of the failed login before the clean reset described here.
====

Use a supported password-recovery procedure if the data must be retained.
Only for a disposable test installation, after backing up anything needed and explicitly accepting the loss of projects, users, images, jobs, and scanner cache, run the following.
Inspect the exact claim names first; do not delete the namespace or unrelated claims.

[source,bash,subs="+attributes"]
----
{prompt_user}kubectl get pvc -n suse-registry
# Set this only after explicitly approving deletion of this test registry's data.
if [[ "${RESET_SPR_DATA:-}" != DELETE_SPR_DATA ]]; then
  printf 'STOP: data deletion has not been explicitly enabled.\n' >&2
  exit 1
fi
{prompt_user}helm uninstall spr -n suse-registry --wait --timeout 5m
{prompt_user}kubectl delete pvc -n suse-registry \
  data-spr-harbor-redis-0 data-spr-harbor-trivy-0 \
  database-data-spr-harbor-database-0 \
  spr-harbor-jobservice spr-harbor-registry --wait=true --timeout=5m
{prompt_user}helm install spr oci://registry.suse.com/private-registry/private-registry-helm \
  --version 1.1.29 -n suse-registry -f "$SPR_INSTALL_VALUES" \
  --wait --timeout 15m
----

Do not delete {sobservability} storage or recreate the k3d cluster.
A clean reinstall has fresh {helm} history, and old {helm} revisions cannot recover deleted data.
After explicit approval, deleting the five {productname} claims and reinstalling resets administrator login to the password configured in `$SPR_INSTALL_VALUES`.

[#pr-observability-install-backend]
=== Installing the backend

[source,bash,subs="+attributes"]
----
{prompt_user}helm repo add suse-observability \
  https://charts.rancher.com/server-charts/prime/suse-observability
{prompt_user}helm repo update suse-observability

[#pr-observability-configure-integrations]
=== Opening the UI and configuring integrations

[#pr-observability-https-access]
==== Accessing the UI through an HTTPS domain

This matches the HTTPS {ingress} setup in xref:pr-observability-https-ingress[].
With `baseUrl: "https://observability.example.com"`, open that URL.
Replace the example domain with your actual host name, and configure DNS, a trusted TLS certificate, and an {ingress} or reverse proxy routing to the {sobservability} router.
Setting `baseUrl` alone does not create any of those resources.
With `ingress.enabled: false`, an external {ingress} or reverse proxy must be configured separately.

[#pr-observability-local-access]
==== Accessing the UI locally through port-forward

For a quick local test instead of the HTTPS {ingress} setup, with `global.suseObservability.baseUrl: "http://localhost:8080"` and `ingress.enabled: false` in `global-otel.yml` as created in xref:pr-observability-prepare-config[], run this in a dedicated terminal:

[source,bash,subs="+attributes"]
----
{prompt_user}kubectl port-forward --address 127.0.0.1 -n "$OBSERVABILITY_NAMESPACE" \
  "service/${OBSERVABILITY_RELEASE}-router" 8080:8080
----

Open `http://localhost:8080` and log in as `admin` using the {sobservability} password, keeping the port-forward running while using the UI.

[NOTE]
====
A port-forward only forwards TCP traffic; it does not add HTTPS or work with an HTTPS-domain `baseUrl`. Do not use `https://localhost:8080` here, and release port 8080 first if it is occupied.
====

[#pr-observability-install-agent]
=== Installing the agent and telemetry gateway

Use `agent-values.yml` as the structure for a private deployment copy.

[#pr-observability-tracefs-debugfs]
==== Process agent crashes on k3d: tracefs or debugfs unavailable

If a node-agent pod shows `1/2` and its `process-agent` logs report `eBPF based network tracer unsupported: tracefs or debugfs is not available`, check mounts inside the k3d nodes, not just on the Linux host.
The chart mounts the node's `/sys/kernel/debug` into the privileged process-agent container.
A host mount at `/sys/kernel/tracing` alone does not provide that path inside Docker-based k3d nodes.

For the local cluster's nodes, install `k3d-entrypoint-observability.sh`:

[source,bash,subs="+attributes"]
----
CLUSTER_NAME=rancher-cluster
OBSERVABILITY_DIR="$PWD/observability"
{prompt_user}(
  set -eu
  for node in "k3d-$CLUSTER_NAME-server-0" "k3d-$CLUSTER_NAME-agent-0"; do
    docker cp "$OBSERVABILITY_DIR/k3d-entrypoint-observability.sh" \
      "$node:/bin/k3d-entrypoint-observability.sh"
    docker exec "$node" chmod 755 /bin/k3d-entrypoint-observability.sh
    docker exec "$node" /bin/k3d-entrypoint-observability.sh
  done
)
----

Confirm that both nodes have `debugfs` at `/sys/kernel/debug` and `tracefs` at `/sys/kernel/debug/tracing` before continuing.
This changes only the node containers' mount namespaces; it does not change host mount configuration.
The script is idempotent and uses the installed k3d entrypoint's `/bin/k3d-entrypoint-*.sh` startup hook: it runs before k3s on subsequent node container starts, and it survives stops and restarts of these containers.
It must be installed again if nodes are deleted, recreated, or added.
Verify the startup-hook mechanism when changing k3d versions.

Recreate only the agent pods so their existing hostPath binds pick up the mounts:

[source,bash,subs="+attributes"]
----
{prompt_user}kubectl rollout restart "daemonset/${AGENT_RELEASE}-node-agent" \
  -n "$AGENT_NAMESPACE"
{prompt_user}kubectl rollout status "daemonset/${AGENT_RELEASE}-node-agent" \
  -n "$AGENT_NAMESPACE" --timeout=5m
{prompt_user}kubectl get pods -n "$AGENT_NAMESPACE" -o wide
----

Keep the process agent enabled.
Confirm that both containers are ready, restart counts remain stable, and the process-agent logs show a running network tracer, not repeated eBPF initialization errors.
Mount availability fixes this specific failure; ingestion credentials and other kernel compatibility issues must still be checked separately.

[IMPORTANT]
====
Debugfs exposes sensitive kernel interfaces: use this workaround only for the intended privileged agent in this local test cluster.
====

[#pr-observability-busy-kprobes]
===== Busy kprobes after the mount fix

For this local k3d installation, protocol inspection and node-agent HTTP tracing were disabled with the following same-version upgrade:

[source,bash,subs="+attributes"]
----
{prompt_user}helm --kube-context "$KUBE_CONTEXT" upgrade "$AGENT_RELEASE" \
  suse-observability/suse-observability-agent \
  -n "$AGENT_NAMESPACE" --version 1.7.19 --reuse-values \
  --set nodeAgent.protocolInspection.enabled=false \
  --set nodeAgent.httpTracing.enabled=false \
  --wait --timeout 5m
----

After the upgrade, confirm both settings are `false` and that the new node-agent pods report `2/2` Ready with zero restarts.
Keep these settings in the private agent values file as shown in xref:pr-observability-install-agent[].
This reduces node-agent protocol and HTTP tracing coverage; it does not disable {productname}'s application-level OTLP traces or the separate {harbor} metrics scraper.
Initial readiness does not establish long-term stability or prove that every shared-kernel kprobe failure is resolved.

The mount fix alone may not be sufficient for stable process-agent operation on both nodes: after initially becoming ready, the worker process agent can restart with `failed to cleanup tracefs` and `kprobe_events: device or resource busy`.

The failing cleanup targets probe names ending in the live server process agent's PID.

When cleanup checks for a PID:
* *Server node's `/proc`* — PID exists (process still running)
* *Worker node's `/proc`* — PID does not exist (process stopped, probe is stale)

Both nodes share kernel-wide kprobe registrations but have separate PID namespaces.
The eBPF manager checks process existence via `HOST_PROC` → `/host/proc`, which reads each node's local PID view.
This is why another node's live probes appear stale.

[WARNING]
====
Do not delete or clear `kprobe_events`: the probes can belong to a working collector.
Do not treat brief `2/2` readiness as proof of recovery; monitor restart counts and successful collection for several minutes.
====

Both process agents remain enabled, but a safe multi-node k3d fix has not been verified.
Preserving full visibility requires either:

* An agent fix that handles shared-kernel + PID-namespace separation
* Nodes with separate kernels (VM-backed nodes instead of k3d)

Mounting the host's `/proc` into collectors is not an equivalent fix—it changes process scope and may expose unrelated workloads.

[#pr-observability-init-error]
==== Pods show Init:Error or Init:0/1

An init container can be waiting for a dependency.
Inspect its logs and pod events:

[source,bash,subs="+attributes"]

{prompt_user}kubectl logs "${OBSERVABILITY_RELEASE}-otel-collector-0" -n "$OBSERVABILITY_NAMESPACE" \

====

[#pr-observability-traces-missing]
==== Traces do not appear

Verify gateway readiness, its HTTP Service port, {productname} tracing values, network reachability, the agent token and backend URL, the OpenTelemetry StackPack, and the UI time range.
Check gateway logs for authentication or export errors:

[source,bash,subs="+attributes"]
----
{prompt_user}kubectl logs -n "$AGENT_NAMESPACE" \
  -l app.kubernetes.io/component=otel-telemetry-gateway --tail=100
----

Sanitize logs and configuration before sharing them.
Gateway acceptance alone does not prove that traces are queryable in the backend.

[#pr-observability-disable-tracing]
=== Disabling tracing or rolling back

Disable tracing without uninstalling the backend or agent:

[source,bash,subs="+attributes"]
----
{prompt_user}helm upgrade "$SPR_RELEASE" oci://registry.suse.com/private-registry/private-registry-helm \
  --version "$SPR_CHART_VERSION" -n "$SPR_NAMESPACE" \
  --reuse-values --set trace.enabled=false --wait --timeout 10m
----

This changes the deployed release, not the override file.
Also set `trace.enabled: false` in your deployment configuration to keep it disabled on subsequent upgrades.

Alternatively, use `helm history spr -n suse-registry` to identify the revision before tracing was enabled, then run `helm rollback spr REVISION -n suse-registry --wait --timeout 10m`, replacing `REVISION` with that number.

[NOTE]
====
A rollback restores the entire selected release revision, not just the tracing values.
====
